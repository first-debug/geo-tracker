# Формат выходных сообщений (UDP)

Координаты объектов отправляются по UDP в двоичном формате
[protobuf](https://protobuf.dev/) (proto3). Схема — [`proto/points.proto`](../proto/points.proto),
пакет `sheremetevo`. Получатель задаётся в группе `[udp]` в `app.ini`
(см. [configuration.md](configuration.md#udp)).

## Датаграмма

Каждая UDP-датаграмма — ровно одно сообщение `Batch`, без дополнительных заголовков
и разделителей: данные датаграммы целиком передаются в `Batch.ParseFromString()`.
Датаграммы независимы, потеря одной не мешает разобрать остальные.

```
Batch                      одна датаграмма
├─ sequence    uint64      номер датаграммы с запуска: 0, 1, 2, ...
├─ sent_at     double      время отправки, секунды Unix-эпохи
└─ frames[]    Frame       кадры в порядке поступления
   ├─ camera_id  uint32    номер камеры, N из [cameraN]
   ├─ timestamp  double    время кадра, секунды Unix-эпохи
   └─ detections[] Detection
      ├─ lat         double   широта точки касания с землёй, WGS84, градусы
      ├─ lng         double   долгота, WGS84, градусы
      ├─ object_id   sint64   id трека nvtracker, -1 — трекер выключен
      ├─ name        string   класс объекта, сейчас всегда "самолёт"
      ├─ confidence  float    уверенность детектора, 0..1
      └─ bbox        BBox     рамка: x1,y1 — левый верхний угол, x2,y2 — правый нижний (int32)
```

## Поля

**`Batch.sequence`** растёт на 1 с каждой датаграммой. По нему получатель видит:

- пропуск номеров — столько датаграмм потеряно в сети;
- номер меньше ожидаемого (сброс к 0) — отправитель перезапустился.

**`Batch.sent_at`** и **`Frame.timestamp`** — секунды Unix-эпохи (UTC) с дробной частью.
`timestamp` берётся из `ntp_timestamp` `nvstreammux`: по умолчанию это системное время
прихода кадра на сервер обработки. Разница `sent_at - timestamp` показывает задержку
обработки и накопления.

**`Frame`** — результат одного кадра одной камеры. Кадр без объектов тоже передаётся
(пустой `detections`): камера работает, но самолётов не видит. Если от камеры нет
кадров, значит, она не даёт видео.

Если объекты кадра не помещаются в одну датаграмму, кадр делится на несколько `Frame`
с одинаковыми `camera_id` и `timestamp`, которые могут прийти в разных датаграммах.
Получателю, которому нужен кадр целиком, стоит объединять `Frame` по паре
`(camera_id, timestamp)`.

**`Detection.lat`, `lng`** — координаты середины нижней стороны рамки
`((x1 + x2) / 2, y2)`, то есть точки касания самолёта с землёй
(см. [calibration.md](calibration.md)).

**`Detection.object_id`** — один и тот же самолёт сохраняет id, пока трекер его ведёт.
Нумерация начинается заново после перезапуска приложения. Трекер ведёт каждую камеру
отдельно: самолёт, видимый двумя камерами, получит разные id; объединение треков между
камерами приложение не делает. Различать треки лучше по паре `(camera_id, object_id)`.

**`Detection.bbox`** — в пикселях кадра детектора (`frame-width` × `frame-height` из `app.ini`).

## Когда отправляется

Управляется ключами группы `[udp]`:

| Ключ | По умолчанию | Описание |
| :--- | :--- | :--- |
| `batch-interval-ms` | `1000` | Кадры копятся этот интервал и уходят пачкой. `0` — каждый кадр отправляется сразу |
| `max-datagram-bytes` | `1400` | Предел размера датаграммы, 256..65507 байт |

- Раз в `batch-interval-ms` накопленные кадры отправляются одной или несколькими
  датаграммами не больше `max-datagram-bytes` каждая.
- Если за интервал кадров не было (все камеры молчат), уходит пустой `Batch` —
  heartbeat: отправитель жив.
- 1400 байт проходят по сети без IP-фрагментации. Большее значение уменьшает число
  датаграмм, но потеря одного IP-фрагмента губит всю датаграмму.
- Отправка идёт в отдельном потоке и не тормозит конвейер. Если поток не успевает,
  лишние кадры отбрасываются.

Объём: кадр без объектов занимает около 15 байт, объект — около 60 байт. При 4 камерах
по 25 fps и интервале 1 с это 100 кадров в секунду, то есть порядка 2–10 датаграмм
в секунду в зависимости от числа самолётов.

## Получатель

Код для любого языка генерируется из схемы компилятором `protoc`. Для Python:

```
pip install protobuf
protoc -Iproto --python_out=tools proto/points.proto
python3 tools/udp_receiver.py --port 6767           # всё содержимое
python3 tools/udp_receiver.py --port 6767 --quiet   # только сводка по датаграммам и потерям
```

`tools/udp_receiver.py` — отладочный приёмник: печатает каждую датаграмму, объекты и
счётчик потерянных датаграмм по `sequence`. Минимальный разбор:

```python
import socket
import points_pb2

sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
sock.bind(("0.0.0.0", 6767))
while True:
    data, _ = sock.recvfrom(65535)
    batch = points_pb2.Batch()
    batch.ParseFromString(data)
    for frame in batch.frames:
        for d in frame.detections:
            print(frame.camera_id, frame.timestamp, d.object_id, d.lat, d.lng)
```

## Совместимость

Схема — proto3: новые поля можно добавлять с новыми номерами, старые получатели их
пропустят. Номера существующих полей менять и переиспользовать нельзя.

До перехода на protobuf сообщения были в JSON, по одному на кадр; массив объектов
назывался `future`, теперь это `Frame.detections`.
